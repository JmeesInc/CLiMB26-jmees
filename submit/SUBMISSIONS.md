## v002_da3_rectify 詳細（2026-08-29）

**v001 からの差分は 1 点**: デコード直後に Kannala-Brandt kb4 → pinhole undistort（+ 有効域クロップ）。
SLAM 本体・連結・出力形式は完全に同一。

- **なぜ**: v001 の LB 惨敗（ATE 28.28mm = ローカル CV の ×6.8、rot 34.0°）の原因を
  `workspace/expB02_fisheye` の対照実験で単離。sim に実キャリブの魚眼を合成すると
  **素通し 19.83mm / 36.0°（LB 実測 28.3 / 34.0 と一致）→ rectify で 5.57mm / 24.0° に回復**
- **キャリブ選択** (`calib_table.py`): 公式 `Calibrations/` の kb4 18 本 + 公開 seq→endoscope 対応
  75/93 系列を焼き込み。動画名の `Seq_(\d+)` で正確に選択、不明時は 18 本平均にフォールバック
  （チャレンジ公開メタデータであり、テストセットへのチューニングではない）
- **有効域クロップ**: rectify 後初フレームで「画像端に接続する暗領域」を flood-fill 検出し
  （内腔の暗部は端に接続しないので保護）、最大内接矩形（ヒストグラム法, 0.7s×1回）で切り出し。
  実 1440×1080 は balance=0 で全有効 → no-op
- **検証**（すべて公式評価器 / 公式起動方法）:
  | 検証 | 結果 |
  |---|---|
  | コンテナ sim 回帰 (`DA3_RECTIFY=0`) | **4.11mm / 93.69 / 6-6**（v001 の 4.13 と一致 = 上位互換確認） |
  | コンテナ 合成魚眼 (rectify ON) | **7.27mm / 100 / 2-2**（ホスト検証と完全一致） |
  | ホスト 正確キャリブ強制 (Seq_0) | **3.35mm**（pinhole 基準 3.11 と同水準） |
  | 実クリップ Seq_001 30s | ステップ長 median 0.0199 vs 素通し 0.0708（**3.6×**）、軌跡が滑らか |

## v003_da3_stride 詳細（2026-08-29）

**v002 からの差分は 1 点**: DA3 を **6 フレームに 1 回**だけ走らせ、間のポーズは
カメラ中心を線形補間・姿勢を SLERP で埋める。出力は全フレーム分なので **TFR 100 を維持**。

- **なぜ**: v002 の LB は ATE 15.762 で **生 ATE なら 4 位相当**だったが、`climb/ATE = 1.5001`
  すなわち **W_t が満額 1.5**。速度が climb を 7.88 点押し下げていた
- **想定外の収穫**: stride は速度だけでなく **ATE も大きく下げた**（実クリップ 9.301 → 5.735, −38%）。
  窓数が減る = 窓間スケール不整合の累積回数が減るため（`daily_reports/20260829.md` §11.4/§12）。
  **sim では ATE がフラットで、この効果は sim CV では一切見えなかった**
- **stride の選択**: 実 4 クリップ sweep で 1→4 で急改善・4〜6 で底・8 以上で崩壊の U 字。
  stride 6 は ATE/rot ともに最良（5.735 / 5.55°）かつ **W_t マージンが厚い**
  （評価機換算 ~0.015 s/f、境界 0.025 に対し余裕 40%超。stride 4 は ~0.021 で余裕が薄い）
- **棄却した施策**（すべて実測で否定、詳細は日報 §11）:
  | 施策 | 結果 |
  |---|---|
  | GT 準拠 Endoscope_07 キャリブ強制 | 9.525 vs 現行 9.301 → **現行が良い**。不採用 |
  | 窓ごと focal 正規化 | `corr(log s, log f比) = +0.088` ≒ 無相関、残差も悪化。不採用 |
  | 重複からの窓間スケール推定 | fixed1 5.756 が最良（damped/raw はすべて悪化）。不採用 |
  | ポーズグラフ / ループクロージャ | 誤差が**ドリフト型でない**（後⅓/前⅓ = 0.18〜0.98）ため効かない。優先度低 |
- **検証**:
  | 検証 | 結果 |
  |---|---|
  | コンテナ 実クリップ 4 本（提出と同一設定） | **5.73mm / rot 5.55 / TFR 100 / 4-4**（ホスト 5.735 と全系列一致） |
  | `validate_submission.py` | **VALID** |
  | ツリー検証 (`test.sh`) | tree OK |
  | コンテナ sim 回帰 (`DA3_STRIDE=1 DA3_RECTIFY=0`) | **4.11mm / 93.69 / 6-6**（v001 の 4.13 と一致 = 後方互換確認、`results_docker_simreg.json`） |

## v001_da3_submap 詳細

- **手法**: DA3 を 8 フレーム窓（3 フレーム重複）で feed-forward 実行し、共有カメラ上で
  剛体整列（回転=カメラ姿勢から、並進=重心、**スケールは推定せず 1 固定**）して単一マップへ連結。
  BA・ループクロージャなし、学習なし
- **CV 内訳 (workspace PNG)**: Seq_0 3.11 / Seq_1 3.26 / Seq_2 3.97 / Seq_3 4.11 / Seq_4 8.63 / Seq_5 8.39 mm
- **コンテナ実測 (`results_docker.json`, 公式起動方法 + 公式評価器)**:
  Seq_0 2.84/100 · Seq_1 3.12/100 · Seq_2 3.78/100 · Seq_3 3.97/100 · Seq_4 2.89/62.1 · Seq_5 8.14/100
  → **Mean 4.13mm / TFR 93.7 / 6-6**。PNG 版より良いのは入力差（mp4 は Seq_4 の先頭200連番のみを含み、
  誤差を支配していた断片化した後半が入らない → ATE 8.63→2.89 だが TFR 77.6→62.1）
- **比較**: ORB-SLAM3 6.63mm（ただし断片別 Sim(3) 整列の恩恵込み・TFR 72.6 / 5-6）、
  expD00 da3pair 6.59、expB01 スケール推定版 7.09、VGGT-SLAM md2 11.73
- **5 ラン**: 手法が決定的なため 1 回計算し 5 ランへ同一内容を書き出す（README に明記）
- **環境要件**: 評価機 RTX 5090 = sm_120 のため **cu128 wheel 必須**
  （開発環境の cu126 torch は arch_list が sm_90 止まりで PTX なし＝評価機で一切動かない）
- **ピーク GPU メモリ**: 19.3GB @ chunk8/res504（5090 の 32GB に収まる。chunk16 は OOM）
- **既知リスク**: (1) 実系列は未検証（ローカル GT 無し）、(2) 1.3 s/frame で長尺系列は高コスト、
  (3) イメージ ~15GB

## v006_da3_rotavg 詳細（2026-08-31 提出済み: LB climb 13.072 = ATE 11.312 × W_t 1.156、rot 6.12、s/f 0.026、ID 9778630）

- **手法**: v004（c12o6_s6 + 自己教師あり LoRA + fp16）を完全踏襲し、**回転のみ後段で差し替え**る
  rotation averaging を追加。ATE は中心座標のみ・RPE_rot は回転のみを見る分解を利用し、ATE 無リスクで rot を改善
- **rotavg パイプライン** (`rotavg.py`): decode 中に 6 フレーム毎の rectify 済みフレームを
  quarter-res PNG で RAM キャッシュ → ALIKED(kp512)+LightGlue → essential matrix → 相対回転エッジ
  （Δ1/4/7/10/13/16 ノードステップ = 6〜96 フレーム跨ぎ）+ DA3 チェーン回転エッジ（w=10 安全網）
  → Huber(2°) IRLS SO(3) averaging + 2 ラウンド外れ値除去 → Slerp 補間で全フレーム回転を置換
- **ENV**: `DA3_ROTAVG=1 DA3_ROT_STRIDE=6 DA3_ROT_KP=512 DA3_ROT_STEPS=1,4,7,10,13,16 DA3_ROT_SCALE=0.25 DA3_ROT_WDA3=10 DA3_ROT_CODEC=png`
- **依存追加**: kornia==0.8.3（lightglue が hard-import）、lightglue vendored、ALIKED/LightGlue 重みは
  `/opt/torchhub` に焼き込み（`--network=none` 対応）
- **CV（コンテナ実クリップ 4 本, `results_docker.json`）**:
  **ATE 4.07（v004 と系列単位で完全一致）/ rot@40 7.01 → 3.90 / TFR 100 / 4-4 / VALID**
  内訳 rot: 001_a 12.38→4.73, 001_c 5.31→4.60, 003_a 2.01→1.08, 003_b 8.35→5.19
- **速度**: 0.114–0.134 s/f @ RTX8000（v004 の 0.117–0.133 と同水準 = rotavg コスト実質ゼロ、W_t リスクなし）
- **チューニング掃引（v004 軌跡 offline）**: w30→w10 で 4.73→4.32、quarter-res kp512 で 4.23（コスト1/4）、
  長エッジ延長で 3.97 (Δ10) → 3.80 (Δ13) → 3.73 (Δ16)。w15 は 3.98 で悪化、ノード 12f 毎は 4.85 で悪化
- **予想 LB**: ATE 11.31 維持（回転差し替えは ATE に影響しない設計 + 実測一致）、
  **rot 7.487 → ~4.2–4.5**（rot 転移係数 ~1.07–1.15）。CCLAB tie-break (3.269) には届かないが、
  PRISM band (rot 4.075) に将来 ATE で入った場合の保険 + score_rot 大幅改善

## v007_da3_rotfast 詳細（2026-08-31 ビルド、push 待ち）

- **手法**: v006 と同一の回転融合を、W_t を発動させないよう構造的に高速化したもの。DA3 側の構成は
  v004 と完全同一（ATE 系列単位一致を毎回帰で確認）
- **v006 からの変更**（すべて速度/バグ修正、回転アルゴリズム自体は同一）:
  1. rectify を quarter-res マップで直接 remap（remap は出力サイズ比例 → 1/16）+ raw ndarray キャッシュ（PNG encode 廃止）
  2. rotavg を**バックグラウンドスレッド化**（decode/DA3 と並行、可視コストは tail のみ）
  3. `_solve` を隣接リスト化（O(nodes×edges×iters) 純 Python 10-26s/クリップ → <1s、数学等価）
  4. LightGlue をノード毎 1 回のバッチ呼び出し（B=6）+ **pruning 明示 OFF**（デフォルト ON がバッチと
     衝突して IndexError → 例外握り潰しでエッジが静かに欠落していたバグの修正）
  5. essential matrix を RANSAC → **USAC_MAGSAC**（CPU 3.4 倍速。offline 精度は ±0.2° 程度の差）
- **ENV**: v006 と同じ + `DA3_ROT_CODEC=raw DA3_ROT_FP16=0 DA3_ROT_ADAPTIVE=0`（steps=1,4,7,10,13,16）
- **CV（コンテナ実クリップ 4 本, `results_docker.json`）**: **ATE 4.07 / rot@40 3.98 / TFR 100 / VALID**
  （rot 内訳 3.94/4.65/0.88/6.46）。tail（可視 rotavg コスト）5.9-19.9s/クリップ
- **速度**: 0.092-0.101 s/f @ RTX8000（v004 の 0.117-0.133 より速い計測。ただし tail の CPU 部分は
  評価機で縮まないため **eval s/f は 0.018-0.021 = W_t 1.00-1.03 のレンジと予想**）
- **予想 LB**: W_t=1.0 なら climb 11.31 / rot ~6（v004 の上位互換）。W_t>1 なら v004 がベストのまま
- **image**: `climb-da3-rotfast:v007` → `docker.synapse.org/syn77166596/climb-da3:v007`

## v012 / v013 詳細（v013 は 2026-09-07 提出済み: **LB climb 5.328 = チームベスト・rank 1** / ATE 5.222 / rot 5.616 / TFR 97.36 / 32-32 / 0.015 s/f、ID 9779574。v012 は未提出）

- **手法**: v010 / v011 に **rotation averaging を有効化**（`DA3_ROTAVG=1`）+ `DA3_RES=448`。
  rotavg は v006/v007 で一度採用したが W_t を払って不採用にしていたもの。今回**実プロファイルを取って
  真のボトルネックを特定し**（`daily_reports/20260907.md` §11）、コストを削って再投入した
- **rotavg の変更点（アルゴリズムは不変）**:
  1. `_solve` のノード毎処理を numpy 化（Gauss-Seidel の数式・掃引順・停止条件すべて不変、
     旧実装との差 **3e-6 deg**）。直列テールが 4 clip 合計 **58.7s → 7.9s**
  2. ALIKED の `detection_threshold` を 0 に（既定 0.2 が top-k をゲートしてキーポイント数を可変にし、
     **v007 で入れたバッチ経路が一度も発火していなかった**）。129 ノード中 12 → ほぼ全ノードがバッチ化
  3. MAGSAC + recoverPose を `ThreadPoolExecutor`(4) に出して GPU 処理と重ねる
     （`finalize` で `(a,k)` ソートし再現性を保持）
  4. `DA3_ROT_STEPS=1,2,6,7,8`（stride 6 → 6/12/36/42/48 フレーム。δ40 を挟む配置）
- **ENV 差分**: v012 = v010 + `DA3_ROTAVG=1 DA3_RES=448 DA3_ROT_STEPS=1,2,6,7,8`

  clip 毎 ATE: 4.72→4.70 / 1.50→1.51 / 1.11→1.10 / 3.46→3.40（**設計どおり不変**）

## v017_mix_lora 詳細（2026-09-07 提出済み: LB climb 5.474 / ATE 5.345 / **rot 5.179** / 97.36 / 32-32 / 0.015、ID 9779602 — **climb では v013 に劣後、score_rot 待避用として保持**）

- **手法**: v013 と完全に同一の構成で、**LoRA adapter だけを差し替えた**もの。
  新しい adapter は `workspace/expB09_lora/scripts/train_lora_mix.py` で学習した
  「実データ自己教師 + sim GT 回転教師」の混合版（step 100）
- **なぜ作ったか**: LB の rot 列で我々は上位陣最下位（5.616 対 CCLAB 3.206）だった。
  原因を追ったところ、**出荷していた LoRA 自体が rot を悪化させていた**と判明:

  | 構成 | ATE | rot |
  |---|---|---|
  | base のみ（LoRA なし） | 3.24 | **3.54** |
  | base + 出荷 LoRA（= v013） | **2.72** | 4.27 |

  cross-window consistency 損失は「入力に鈍感な滑らかな回転」でも満足してしまうため
  （`train_lora.py` のコメントが予言していた挙動）、並進・スケールの一貫性（ATE）を
  買う代わりに回転の忠実性を失っていた。`DA3_ROT_WDA3` を 10→5→2→0.5 と下げても
  rot は 4.27→4.33→4.82→5.03 と単調悪化し、**rotavg 側では回収不能**と確定
- **解決**: 同じ adapter に **sim の正確な相対回転**を同時に教える。
  sim 単独（`train_lora_sim.py`）は実データ上で完全に無効だったが（6 点すべて base と 1% 以内）、
  実データの目的関数に縛られた状態で sim 勾配を受けると効いた。
  過去に同じ役割を LightGlue 蒸留で狙って失敗している（3.35→4.42）ので、
  **教師が実測かGTか**が分かれ目だった
- **学習設定**: 実データ側は出荷 adapter と同一（clips / views 12 / overlap 6 / lr 5e-4 / w_anchor 0.2）。
  sim 側は**回転のみ**（並進方向損失は ATE を壊すので除去）、stride 2 + 窓内最大回転 25 度以下 +
  カメラが実際に移動、でフィルタ（1728 窓中 1297）。res 448 = **v013 の推論解像度に一致**
  （出荷 adapter は 504 学習で不一致があった）。ステップ交互、p_sim 0.5
- **チェックポイント選択**: step 150 で両軸悪化（2.943 / 4.681）→ **step 100 が最良**。
