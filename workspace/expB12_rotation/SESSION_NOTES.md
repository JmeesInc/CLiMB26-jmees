# expB12_rotation — 回転精度の改善（tie-break 攻略）

## 動機（2026-08-31）
- v004 LB: ATE 11.311 で CCLAB(11.241) と 0.62% 差 = **5% tie band 内**。tie-break は score_rot で
  7.487 vs 3.269 の完敗 → **rot@40 < 3.27 が rank 2 のもう一つの条件**（ATE≤10.71 と並ぶ二本目の道）
- **構造的な好条件**: ATE は中心座標のみ・RPE_rot は回転のみを使う → 軌跡ファイルの回転だけを
  別ソースに差し替え可能（**ATE 無リスクの接ぎ木**）

## 誤差の構造（既知）
- 連鎖の回転誤差はランダムウォーク: keyframe ステップ誤差 ε が √(スパン/ストライド) で蓄積。
  rot@40 < 3.27 には **ε ≲ 1.2°/step** が必要。現状の DA3 連鎖は ε ≈ 2〜3°
- LoRA(v004) は並進整合を最適化した副作用で回転を悪化（5.9→7.5）
- 実証済みの上限例: ORB-SLAM3 が追跡区間で **1.24°@40**、VGGT-Ω が 003 系列で 1.75°@40
  → 特徴点/対応ベースの回転は feed-forward 姿勢ヘッド回帰より一桁近く良い

## 手法調査の要点
- **回転平均化（rotation averaging / SO(3) synchronization）**: 相対回転グラフから大域回転を
  ロバスト最適化（geodesic + Huber）。古典（Hartley IJCV'13, Chatterjee-Govindu L1-IRLS, Shonan）
  は数百ノードならミリ秒級。2025-26 も活発（不確かさ付き再訪 arXiv:2303.05195、
  Global SfM × feed-forward の融合 arXiv:2605.26103、FUSER CVPR2026 等）
- feed-forward 系（VGGT/DA3）の姿勢は対応ベース + 幾何検証（essential/BA）での精緻化が定石
  （VGGSfM/MASt3R-SfM 系の設計思想）。DA3 の姿勢ヘッドは回帰であり回転の高精度化には
  epipolar 幾何のような硬い拘束が無い

## 計画
1. **edge_rot_probe**（実行中）: keyframe ペアの相対回転誤差を DA3 連鎖 vs ALIKED+LightGlue+essential
   vs identity で GT 比較。ε≲1.2° に届くソースを特定（これが go/no-go）
2. 届くなら: 特徴点エッジ（隣接+スキップ）+ DA3 エッジで**回転平均化** → 最良 ATE 軌跡（v005）の
   回転だけ差し替え → 実 CV の rot@40 で判定 → v006
3. マッチ失敗フレーム（スペキュラ・ブラー）は DA3 回転にフォールバック（グラフの重み付き融合が自然）

### v006 の設計変更（v005 LB=13.58 を受けて）
- v005 の dense 窓は LB で位相平均（13.6 予測）に着地 → **ATE の土台は転移実績のある v004（係数 2.78）に戻す**
- **v006 = v004（c12o6_s6 + LoRA + fp16）+ rotavg**。狙い: ATE 11.31 維持 + rot 7.49 → ~3.7-4.0
- 効能の現実的評価: CCLAB tie-break の反転には rot<3.269 が必要で届かない公算だが、
  (a) 将来 ATE が PRISM band (≤11.2) に入った時に rot 4.075 を下回って勝てる保険、
  (b) score_rot の見た目・write-up 上の完成度、の価値がある
- 統合実装: 回転ノード（6フレーム毎）を decode 中に half-res JPEG でキャッシュ（長尺でもメモリ安全）→
  チェーン補間後に rotavg.refine() が回転のみ差し替え。lightglue を vendor、ALIKED/LG 重みを
  /opt/torchhub に焼き込み（--network=none 対応）。処理時間は processing_seconds に計上（正直側）

## v006 展開チューニング（v004 実軌跡上、2026-08-31）

コンテナ初回（half-res kp768 w30）: rot 7.01→4.60、ATE 不変、ただし +0.06 s/f で W_t 危険。
offline 掃引（v004 軌跡、ATE は全構成 4.07 不変）:

| 構成 | rot@40 |
|---|---|
| w30 half kp768 Δ1/4/7 | 4.73 |
| w10 half kp768 Δ1/4/7 | 4.32 |
| **w10 quarter kp512 Δ1/4/7 (light)** | **4.23** |
| w10 ノード12f毎 Δ1/2/3 | 4.85（短エッジ喪失で悪化） |
| w3 light Δ1/4/7 | 4.39（w下げすぎは悪化） |
| w1 light Δ1/4/7 | 4.40 |
| w3 light Δ1/4/7/10 | **4.07**（Δ10=60f エッジが決定打） |

学び:
- v005 軌跡では fused 3.46 だったが v004(LoRA) 軌跡では ~4.1-4.2 が下限圏。LoRA のチェーン回転劣化は DA3 安全網エッジ経由で fused にも残留する
- w_da3 は 10 が最適域（30 は引き戻し、≤3 は特徴エッジ誤りへの保険喪失）
- quarter-res kp512 は half-res kp768 と同精度でコスト 1/4 → コンテナ実測 0.096-0.109 s/f（v004 の 0.117-0.133 より速い = rotavg コスト実質ゼロ）
- コンテナ(JPEG q92 キャッシュ)は offline(PNG) より +0.4° 程度悪い(4.64 vs 4.23): JPEG 劣化がマッチングに響く

## v006 LB (2026-08-31, ID 9778630) と v007 高速化

v006 LB: **ATE 11.312（v004 と同一 = 回転差し替えの ATE 不変性が本番成立）/ raw rot 7.487→6.12 /
しかし s/f 0.017→0.026 → W_t=1.156 → climb 13.072（ベスト更新ならず）**
- W_t 逆算で **評価動画 ~50fps、予算 T≤0.0198 s/f** が確定
- 敗因: rotavg の CPU 律速部（full-res remap→resize, PNG encode）+ LightGlue/ALIKED の細切れ GPU 呼び出し
  オーバーヘッドは評価機の速い GPU でも縮まない（DA3 の 0.249 係数は適用外）
- rot 転移 3.90→6.12 = 係数 1.57（従来 1.07-1.15）: Δ16 長エッジ調整の 4 クリップ CV 過適合疑い

v007_da3_rotfast 反復:
- iter1（quarter-res 直接 remap マップ + raw ndarray キャッシュ + steps Δ1/4/7/10）:
  rot 4.43 / ATE 4.07 / VALID。rotavg 実測 **170-200ms/node（ローカル）** → 評価機換算 ~+4-6ms/f で予算超過見込み
- iter2（+ autocast fp16 + LightGlue adaptive early-exit (depth 0.9/width 0.95) + steps Δ1/4/7）: 検証中。
  目標 <70ms/node ローカル

### v007 高速化の反復（コンテナ実測、ATE は全て 4.07-4.08 / VALID）
| iter | 変更 | rot | rotavg コスト |
|---|---|---|---|
| 1 | quarter map 直 remap + raw cache + Δ1/4/7/10 | 4.43 | 170-200ms/node（直列） |
| 2 | + autocast fp16 + LG adaptive + Δ1/4/7 | 4.97 | 135-165ms/node（20%減止まり・精度劣化）→ 却下 |
| 3 | **バックグラウンドワーカー化** + 精度構成復帰（Δ…16, fp32） | 4.07 | tail 10.8-26.2s = ほぼ重ならず |
| 4 | + _solve 隣接リスト化（O(n·m)→O(Σdeg)、数学等価） | 4.07（同一） | tail 22.8s → solve は ~3s しか占めず |
| 5 | + LightGlue ノード毎バッチ呼び出し（6→1 call, B=6） | 検証中 | |

判明した構造:
- ボトルネックは LightGlue のペア毎呼び出しオーバーヘッド（~120ms/node）。fp16/adaptive では縮まない
- ワーカーは DA3 と GPU を取り合ってローカルではほぼ重ならない（tail ≈ 全作業）
- v006 の実測: ローカル ~220ms/node → 評価機 54ms/node = GPU 呼び出し系は評価機で ~1/4 に縮む
  （CPU 純 Python の solve はそのまま残る → 隣接リスト化が必須だった）
